# Map navigation and view sharing — 2026-09-19

## Use cases and acceptance criteria (before implementation)

1. A rider chooses routes and filters, then uses Back/Forward or opens a saved hash. The route geometry, stops, vehicles, route selection, system/direction toggles, and search text must agree with the restored state. Navigation creates one history entry per committed user change; rendering does not create duplicate entries.
2. A rider quickly switches routes or navigates back while network requests are pending. Only the newest navigation may publish metadata, render graphics, restart polling, or open a route popup. Page exit and a new directions session revoke obsolete work.
3. A rider chooses Clear all filters after typing a query or changing panels. Route/date/time/system/direction filters return to defaults; search text/results and panel drafts reset and close. The rider's chosen location remains their local preference. Back can restore the prior filter view.
4. Browser navigation during walking directions updates the desired filter state and controls without replacing active navigation graphics. Exiting directions applies the latest desired state. Existing cold-start recovery retains its cancellation and selection protections.
5. A rider activates Copy view link by keyboard or pointer. The copied absolute link contains only the current route/date/time/system/direction filters and the application origin/path. It excludes query parameters, coordinates, account tokens, and local planned-location data. Success is announced; blocked or missing Clipboard support exposes a labeled, selected URL for manual copy and a dismissible fallback.
6. A signed-out recipient opens a shared view and signs in (including terms acceptance), or visits the sign-in page with an existing session. The map route and recognized filters survive authentication. The return target is always the local map page: external URLs, other application paths, query strings, location coordinates, and tokens must never become a redirect target or be forwarded. This follow-up acceptance case was added before its implementation after integration review identified the missing sign-in handoff.

## Implementation plan

- Introduce a small navigation coordinator with request ownership and injected rendering/control callbacks. Route all map filter, history, reset, location, and directions-exit restoration through it.
- Extend URL synchronization with explicit committed-history writes, restore listeners, and canonical safe share-link serialization.
- Add one guarded current-state restoration method to the filter controller, sharing guards with startup recovery. Synchronize panel drafts and search presentation through explicit component APIs.
- Add an accessible Copy view link control and self-contained feedback/fallback UI.
- Carry a sanitized map hash through the authentication URL and apply the same allowlist when returning after login or the existing-session shortcut; test privacy, invalid targets, and the login handoff without changing authentication semantics.
- Verify history restoration and stale-request rejection with controlled promises; verify filter/reset component behavior and share privacy/fallback in jsdom. Run the complete client suite, client typecheck, and lint using the portable Node 24 runtime. The main task performs live browser checks and deployment separately.

## Results

- Implemented `MapNavigationCoordinator` as the owner of committed filter/history changes, with a 30-second deadline, explicit cancellation, and guards against newer navigation, account, directions, stop, and page lifecycle changes. `FilterController.restoreView` redraws the current filter state and prevents overlapping startup recovery from replacing it.
- Back/Forward and manual hash changes restore graphics and controls. Committed selections create history entries; internal redraws replace the current entry. Restored date/time filters use the complete cached route catalog, including CMU metadata and recovered colors.
- Clear all filters resets route/date/time/system/direction state, both search inputs, panel drafts and visibility. Local planned location remains unchanged. Canceling a route draft restores its committed selection.
- Added a named Copy view link button, announced success, and an accessible native dialog with a selected read-only URL when clipboard access is unavailable. Only known public filter fields are serialized; query strings, coordinates and account tokens are excluded.
- Shared views now survive sign-in and terms acceptance. The authentication handoff carries an allowlisted map fragment on `/auth`; successful authentication returns to the fixed local map path. A validated existing session follows that handoff directly, while an ordinary authentication page retains its previous behavior. Expired-session redirects use the same sanitizer. No user-controlled return URL is accepted.
- Automatic GPS/default-location repaints defer while a rider is selecting/viewing a stop, a popup is open, directions are active, or foreground navigation is pending. Explicit filter/location navigation remains intentional. Canceled route schedule requests leave a retry message scoped to their own popup; late replies cannot register obsolete popup callbacks.

Validation using portable Node 24: `npx tsc -p tsconfig.client.json --noEmit`, `npx eslint client tests/client.tests`, and `npx jest tests/client.tests --runInBand --coverage=false` passed. The integrated client run contained 184 tests in 23 suites, including concurrent live-tracking and planned-location improvements. This cycle added 41 tests covering history/cancellation/deadlines, actual stale map rendering, control reset/draft state, clipboard privacy/fallback, color/CMU catalog preservation, passive location exclusions, route-popup cancellation, and the sign-in handoff. Authentication tests cover route/filter preservation, invalid/external destinations, credential/location stripping, login/terms success, failed login, and the scoped existing-session shortcut. Live desktop/mobile QA is recorded by the main task.
