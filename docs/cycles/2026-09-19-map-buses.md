# Bus marker clarity — 2026-09-19

## Use cases and acceptance criteria (written before implementation)

1. A rider follows a moving bus: identify it as a compact circular, route-colored badge with an upright bus symbol. A triangle outside the circle indicates travel bearing, with 0° north, 90° east, 180° south, and 270° west. Westbound vehicles must not mirror or invert the icon.
2. A rider zooms the map: keep bus markers legible without obscuring nearby stops or street names. Bound the complete marker canvas to 32–44 pixels, keep its map anchor at its center, and use a safe default for invalid zoom input.
3. A feed supplies an unusual heading: normalize finite negative or multi-turn bearings; omit the direction triangle when the heading is missing or invalid rather than imply northbound travel.
4. A bus is detoured: retain a distinct amber fill. Ordinary buses retain validated hexadecimal route colors; malformed colors use a neutral transit-blue fallback and cannot introduce markup into the SVG.
5. A rider shares or inspects the marker asset: generate the icon locally without embedding vehicle IDs, coordinates, timestamps, route names, or remote resource references.
6. A live feed omits its bearing: preserve that unknown value from provider decoding through the shared vehicle contract. GTFS-RT protobuf defaults must not turn an omitted field into a northbound heading; an explicitly supplied zero remains valid. TripShot null/nonfinite bearings and malformed TrueTime heading strings remain unknown. Add provider conversion regressions before final integration.

## Findings and implementation plan

The previous `bus-icon.ts` rendered a side-on rectangular bus, mirrored westward bearings, defaulted unknown headings to north, and grew to a 100-pixel canvas. This made heading interpretation and dense-map scanning harder. Replace its SVG with a restrained circular badge, white rim and subtle dark edge, fixed upright bus pictogram, and independently rotated external pointer. Preserve the existing `url`, `anchor`, and `size` contract so polling, marker selection, and reporting behavior remain unchanged.

Validate the decoded SVG through focused tests for cardinal and normalized headings, absence of a pointer for invalid headings, bounded size and centered anchor, detour/fallback colors, and exclusion of supplied metadata or remote references. Run focused ESLint and the client TypeScript check. Integrated browser and production acceptance belong in the cycle execution record.

## Results

Implemented the circular badge with an upright front-facing bus pictogram and a separate external heading triangle. The white rim, white triangle outline, and subtle dark edge separate the icon from route geometry and light map surfaces. Detours use amber `#d97706`; invalid route colors fall back to blue `#2563eb`. Unknown headings render the same badge without a directional claim. Markers use 32–44 pixel canvases (40 pixels at zoom 14) and center anchors, including fractional centers at odd canvas widths.

Focused icon validation on portable Node **24.20.0** passed: **33 tests**, ESLint for both changed TypeScript files, and the client TypeScript check. Tests cover all four compass directions, normalization, missing/invalid headings, size bounds, center anchors, valid and malformed colors, detour colors, and exclusion of vehicle metadata/external resources. No dependencies, additional network requests, map selection behavior, or database configuration were introduced.

Integration review found that the PRT and CMU provider converters replaced absent bearings with zero before they reached the renderer. The shared `IVehicle.heading` contract now permits absence. The PRT converter requires an explicitly supplied, finite protobuf bearing (an inherited protobuf default of zero is not an observation); TripShot retains only finite numeric bearings; TrueTime retains only nonempty, fully numeric finite heading strings. Explicit zero remains valid. Unknown headings are omitted from JSON responses, and the live endpoint shape assertion accepts this documented optional field.

Added **26 provider conversion tests** using the public services, mocked feed responses, and real GTFS-RT encoding/decoding. Together with icon, polling lifecycle, and existing TrueTime color/detour regressions, **93 tests across five suites passed**. Server and client TypeScript checks and focused ESLint passed on Node **24.20.0**. Provider tests verify absent versus explicit zero, valid bearings, malformed/nonfinite values, and omission of unknown headings from serialized responses; no production network calls or database writes were made.

Integrated browser and production appearance checks are recorded in the overall cycle execution record. Heading correctness still depends on the upstream feed providing a real bearing; this renderer omits its pointer when a bearing is absent or invalid.
