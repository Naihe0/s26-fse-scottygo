# Backend performance and reliability cycle — 2026-09-19

Status: scope approved; implementation and focused verification complete.

## Evidence and chosen scope

1. `server/models/transit.model.ts#getDetours` independently reads Mongo and fetches the all-routes TrueTime endpoint for each simultaneous cache miss. `getDetoursWithGeometry` also requests identical upstream geometry on every call. Concurrent map users can duplicate calls while data has not changed.
2. `server/controllers/transit.controller.ts#getNearbyStops` accepts every positive finite `radiusMeters`. An effectively global radius includes every candidate stop and produces an unnecessarily large nearby-stop response. The normal flow uses 1,000 meters, expanding to 2,000 meters if needed.

The account last-administrator check still has a count/update race. A safe cross-instance invariant requires a larger database change, so this cycle will not alter it. No vehicle endpoint contract changes are proposed.

## Use cases and acceptance checks

### Several users open detour information together

- Concurrent detour metadata cache misses share one upstream fetch/write.
- Concurrent geometry requests for the same route share one upstream request.
- Repeated geometry reads reuse results for at most 60 seconds, including empty successful results. Results still include geometry-only detours if metadata omits their route linkage.
- The geometry cache has an explicit fixed capacity and eviction policy; arbitrary route keys cannot grow memory without bound.
- Failed requests release their in-flight state and can recover on a later call.
- Cache invalidation cannot be undone by a stale pending request.
- Different route requests remain independent and preserve the existing response shape. No database or provider credentials are needed for tests.

### A nearby-stop query supplies a very large radius

- A radius over 10,000 meters gets the existing `OutOfBounds` client error / HTTP 400 before route collection or stop-distance work.
- Model callers receive the same bound, rather than relying only on HTTP parsing.
- Positive radii up to 10,000 meters remain accepted.
- Omitted radius retains 1,000 meters and the existing 2,000-meter automatic expansion behavior. Coordinate/filter validation remains intact.

## Results

The baseline regression tests reproduced both redundant upstream work and the unbounded radius. The same fixtures now pass:

| Workload | Before | After |
| --- | --- | --- |
| 20 concurrent detour metadata cache misses | 20 upstream calls | 1 upstream call and 1 Mongo write |
| 12 concurrent geometry reads for one route | 12 upstream calls | 1 upstream call |
| Repeat geometry reads before 60 seconds | One call per read | Reuses the successful result |
| Nearby radius `1e20` | HTTP 200 / model accepted | HTTP 400 / model rejects before collecting routes |

`TransitModel` now coalesces metadata work, keeps at most 64 geometry result entries with least-recently-used eviction, and allows at most 64 distinct pending geometry requests. Geometry keys are trimmed, uppercased, and limited to 64 alphanumeric/underscore/hyphen characters. Successful geometry results expire after 60 seconds, including empty results. Failed requests are not cached. Cache clearing invalidates pending geometry results and waits for metadata writes already in progress before deleting the Mongo entry.

TrueTime HTTP 200 responses can still contain provider errors. Authentication, quota, internal, and unknown error envelopes now throw for both detour metadata and geometry, so these failures cannot become long-lived empty cache entries. The exact documented `No data found for parameter(s)` message remains a valid empty result: the guide defines it as no matching records and applies it to `getdetours` and `getpatterns`. Zero-record success envelopes and ordinary patterns without detour IDs are also valid empty results. Mixed no-data/error envelopes still fail. See the official [TrueTime API guide, sections 3.7, 3.12, and 6](https://truetime.portauthority.org/bustime/apidoc/docs/DeveloperAPIGuide3_0.pdf).

The shared radius validator rejects non-finite, non-positive, and over-10,000 meter inputs at both controller and model boundaries. The existing 1,000-meter default and 2,000-meter fallback remain covered by discovery tests.

## Verification and limits

- Focused Jest run: **5 suites, 109 tests passed**, including provider envelope failures/recovery, no-data compatibility, normalized keys, TTL boundary, LRU eviction, pending-work cap, invalidation races, route filtering, and radius boundaries. The suites were `transit-query-cost`, `truetime-detours`, `track-bus`, `transit-validation`, and `discoverstops` under `tests/server.tests/unit.tests`.
- `npx tsc --noEmit` passed; ESLint passed for all changed server/test files.
- Tests mock provider and persistence boundaries; no live database, feed, or production data was changed.
- Coalescing and geometry caching are per process. They do not coordinate multiple Render instances. The existing scheduled full-cache refresh is separate from request coalescing.
- At 64 distinct pending geometry requests, additional distinct routes receive the existing metadata-only fallback and can retry on a later request.
- **Existing metadata freshness remains 24 hours**, including legitimate empty results. This cycle improves request costs and distinguishes errors; it does not shorten that policy. Previously cached empty metadata can remain until expiry or explicit cache clearing. Shorter metadata freshness remains a separate follow-up for rider-visible detour changes.
