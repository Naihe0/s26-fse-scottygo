# Frontend audit — 2026-09-19

This audit reviews the five shipped pages, their supporting components, state, API adapters, and map controllers. Verification combines source review and focused jsdom tests. Live Google Maps/browser verification is tracked separately by the main audit; these tests do not establish live feed availability, actual browser layout, GPS accuracy, or server authorization.

## Fixed findings

| Priority | Confirmed problem and effect | Change and evidence |
| --- | --- | --- |
| P1 | Notification messages and feed text were inserted directly into `innerHTML`, creating an HTML-injection boundary for stored reports and upstream strings. | Added `utils/html.ts` and escaped notification cards, live popups, search/route results, subscription cards, report restoration, popup headings and dock labels. DOM regressions supply HTML-looking strings and verify literal text with no injected image elements. |
| P2 | Registration could remain enabled after a valid field changed; an old validation result could overwrite the latest input. Account editing had the same response-order issue. | Field validation uses request versions and invalidates pending work on changes/reset. Registration disables submission while validation or registration is pending. Tests exercise late successful validation after a newer error. |
| P2 | Accepting terms reported success even when the subsequent login failed; failed attempts cleared the pending credentials and broke retry. | Agreement flow validates the authenticated response, keeps the modal retryable on failure, and disables concurrent acceptance. Test verifies failed login, retry, and token storage. |
| P2 | A throttled login reused the `UnauthorizedRequest` error name, which could incorrectly open the terms dialog. | Terms recovery now requires HTTP 401 as well as the error name; HTTP 429 displays the server's retry message and restores the login button. A focused regression covers this integration case. |
| P2 | Transit/notification search responses could reopen or overwrite a cleared/newer search. | Request versions discard obsolete results; clearing notifications also cancels queued debounce work. Regression tests resolve responses out of order. |
| P2 | A prior stop request or refresh could replace a newer/dismissed popup. Arrival refresh only edited existing rows, so a popup with zero arrivals never gained rows. Selected row indices could silently select another bus. | Stop lifecycle versions reject obsolete work; refreshed lists rebuild all rows and retain selection by vehicle/route/stop identity (scheduled rows by arrival). Tests cover empty-to-populated refresh and reordered selected buses. |
| P2 | Saved filter URLs lost both-off states and date/time, while default links retained previous selections. | Full default restoration, explicit empty filters, validated date/time parsing, and local-date serialization. Both-off systems now synchronize URL and do not request nearby stops. |
| P2 | Subscription failures could reject without user feedback and leave controls unusable; repeated clicks raced. | Pending mutation guard, error feedback, safe retry, partial-load recovery, and actual disabled limit controls. DOM tests simulate a network rejection. |
| P2 | Navigation and transit options required a pointer; icon names were exposed as control names; subscription dialog had no accessible close path; shared filter checkboxes were unnamed. | Button semantics, accessible names/states, option-derived names for every shared filter checkbox, keyboard search selection, dialog Escape/close and focus management, named location options, keyboard arrival rows and dock tabs, and removal of browser zoom restrictions. |
| P2 | In-memory route subscriptions could survive a token change or a stale previous-user response. | Cache ownership follows the current token and response ownership is checked before populating it. Both cases are covered by tests. |
| P2 | Pending map bell mutations and user lookups could complete after another tab switched accounts, affecting the newer session. | Bell responses/errors check their captured token before cache, socket, toast, or icon effects. User lookups use a captured authorization token and discard old-session success/401/error responses before returning data or clearing credentials. Regression tests cover successful/rejected mutations, stale user data, and stale 401 responses. |
| P2 | The report form closed before its request completed, discarding the user's draft on failure. | Explicit success/error callbacks, a pending state, duplicate-submit protection, a 15-second request timeout, and versioned completion preserve the draft for retry and protect newly opened forms from old responses. Regression tests cover retry and stale completion. |
| P2 | A page opened while GTFS was warming cached an empty bulk response as complete. Subsequent health checks refreshed only colors, leaving the route/stop cache empty; the GTFS-only unhealthy state also produced an empty banner. | A controlled false-to-true readiness regression establishes the recovery gap independently of live marker-count observations. The map now shows a loading message and retries readiness every five seconds for two minutes, then every minute. Recovery reloads bulk/required CMU metadata and reapplies current location, route, system, direction, and date/time context. It defers during directions or a selected stop/popup, rejects superseded work, preserves the loading state after failed requests, and revokes work on page exit or a 30-second attempt deadline. Color retries remain pending until applied. |

## Validation

Commands used for frontend verification:

```powershell
npx tsc -p tsconfig.client.json --noEmit
npx eslint client tests/client.tests
npx jest --runInBand --coverage=false tests/client.tests
```

New tests cover auth validation/recovery, token-scoped subscriptions, transit search ordering and keyboard operation, notification/live-popup escaping, subscription failure/dialog behavior, filter URL round trips, popup/report rendering, prediction request/refresh lifecycles, and cold-start transit recovery. Recovery regressions include failed bulk/CMU/nearby/stops/date-time requests, legitimate empty results, current filters, active/new directions and stop sessions, account changes, unload, stalled nested requests, retry backoff, and blocked color updates. The previous walking-directions, restoration, and vehicle-tracker suites remain in the full client run.

## Remaining improvements and limits

1. **P2 — Coordinate visual map restoration on `hashchange` and filter reset.** `state/url-sync.ts` restores state, while `map.ts` applies route rendering during initial load and UI events. A shared asynchronous filter-restoration coordinator should also reapply map graphics and synchronize panel control values during browser navigation. Clear all filters resets state/URL/rendering but leaves the transit-search text (for example, `61C`) visible; it currently clears only the route-selector control. The URL tests prove serialization/state restoration, not these visual transitions.
2. **P2 — Complete modal focus management.** Subscription sheet and header are improved. Auth/account confirmation dialogs, bus report steps, and onboarding still need consistent focus entry, trapping, Escape policy, and focus restoration. Add full keyboard/screen-reader browser checks; jsdom does not validate native `inert` behavior or visual focus styles.
3. **P2 — Distinguish feed failure from no service.** Several `services/transit-api.service.ts` methods return empty arrays for both valid empty results and failures. Typed result states would let route/arrival UIs communicate errors without implying there is no service. Notification search also still couples notification/alert fetch failures via `Promise.all`.
4. **P3 — Consolidate recurring client infrastructure.** Fetch/auth/error handling, toast styling, mute persistence, and modal behavior are duplicated. Prefer small shared services while retaining the existing map-provider abstraction. `account.ts` and `filter-controller.ts` remain large modules deserving gradual extraction by responsibility.
5. **P3 — Audit remaining lifecycle and persistence edges.** Location-search document/state listeners lack disconnect cleanup; animation-only cleanup can leave UI elements behind when animations do not finish; stored planned coordinates should be checked for finite geographic bounds. Browser-level cross-tab logout/mute behavior and reconnect retries need dedicated coverage.
6. **Product decision — Restore or remove dormant UI.** Calendar/time pickers and dark mode exist in source without current page controls. Decide whether to ship them, then test the complete flow, or remove their unused code and stale comments.
